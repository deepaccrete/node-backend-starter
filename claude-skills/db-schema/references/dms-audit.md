# DMS Database — Convention Audit

**Purpose.** A measured, evidence-backed statement of the house rules that govern this
PostgreSQL schema, written so it can be lifted directly into a Claude skill that authors
new tables, columns and migrations without a human re-explaining the style each time.

Every rule below carries its **adherence count** and its **named exceptions**. Nothing here
is aspirational — it is what the schema actually does today, plus a clearly separated
register of places where it contradicts itself.

| EXCLUDE constraints | 2 |
| Views | 2 (`vw_salesperson_day_summary`, `vw_subscription_usage_history`) |
| **Triggers** | **0** |

The zero is load-bearing: **nothing in this database is maintained by the database.**
`updatedat` is written by the application on every UPDATE, soft deletes are application
UPDATEs, and every derived total is either a `GENERATED … STORED` column (5 of them) or
recomputed in a model. A rule that says "the DB will handle it" is always wrong here.

## 2. Tier A — invariants (100% or one-off exceptions only)

These hold everywhere. A new table that breaks one of them is a bug, not a variation.

### A1. Every table has `id` as its sole primary key

`111/111`. Named `<tablename>_pkey` in `111/111` cases — always the Postgres default name,
never hand-named.

- `serial4` (int4) — **57 tables**
- `bigserial` (int8) — **52 tables**
- `int8 GENERATED BY DEFAULT AS IDENTITY` — **2 tables** (`creditnotemaster`,
  `creditnoteitem`) — *deviation, see D2*

**Rule:** `serial4` for masters/reference data; `bigserial` for anything transactional
(documents, line items, ledgers, logs, stock movements). The split is semantic and
consistent: every `*lineitem`, every document master (`invoicemaster`, `grnmaster`,
`salesordermaster`, `purchaseordermaster`, `paymentmaster`, …), every log and every
inventory table is `bigserial`.

### A2. All identifiers are lowercase, and effectively unseparated

**0 of 2 061 columns contain an uppercase letter.** Same for all 111 table names.

Word separation is *absent* — `productname`, `organizationid`, `createdat`,
`totaltaxamount`, `reconciliationstatus`, `maximumretailprice`. Only **25 of 2 061
columns (1.2%)** contain an underscore, and they cluster into two identifiable pockets
(see D1). There is **no ORM and no naming-translation layer** — a column name in SQL is
the exact key the frontend receives, so the name is a public API surface.

### A3. `createdat` is universal and identically defined

`111/111` tables, every one of them:

```sql
createdat timestamp DEFAULT now() NOT NULL
```

Zero variance. This is the single most consistent thing in the schema.

### A4. Timestamps are `timestamp` (no time zone)

277 `*at` columns; **276 are `timestamp without time zone`**, 1 is `timestamptz`
(`salesordermaster.cancelledat` — *deviation, see D3*). `date` is used for business dates
(`invoicedate`, `duedate`, `paymentdate`, `effectivefrom`) — 65 columns, never `timestamp`
for those.

### A5. Booleans are `int2` (`smallint`) holding 0/1

**223 `int2` columns**; exactly **1 real `bool`** in the whole schema
(`planmaster.isvisible` — *deviation, see D4*). Postgres `boolean` is not used and
`true/false` never appears as a default outside that one column.

Of the 223: 191 are `is*`, 6 are `can*` (the `rolepermissionmap` grid), 2 are `allow*`,
1 is `auto*`. The remaining ~23 are genuinely small integers reusing the type
(`sortorder`, `failedloginattempts`, `priority`, `durationdays`, `limitgroup`,
`devicebattery`) — that reuse is deliberate and fine.

Defaults: `0` × 173, `1` × 46, `2` × 1, none × 3. **210/223 are `NOT NULL`.**

### A6. Enums are `varchar` + optional CHECK — never a Postgres `ENUM` type

**Zero `CREATE TYPE … AS ENUM` in the schema.** Every state machine, category and mode is
a `varchar(20)` or `varchar(30)` holding a lowercase `snake_case` token. Widening a state
machine is an app change (plus a CHECK edit where one exists), never a `ALTER TYPE`.

Value casing is `lower_snake_case` (`tax_invoice`, `partially_received`, `on_leave`,
`raw_material`, `quality_check`) with three deliberate uppercase exceptions where the
token is an external/industry code: `httpmethod` (`GET`/`POST`/…), `valuationmethod`
(`FIFO`/`LIFO`/`AVCO`/`STANDARD`), `licencetype` (`LMV`/`HMV`/`HGMV`/`MCWG`/`Other`).

### A7. Deletes are soft, and no FK cascades

`isdeleted int2 DEFAULT 0 NOT NULL` on `107/111` tables — always exactly that definition,
zero variance in type or default.

**All 304 foreign keys use the default `NO ACTION`.** There is not one `ON DELETE CASCADE`
and not one `ON DELETE SET NULL` in the schema. Rows are never physically removed, so
cascade semantics would be dead code — and a hard `DELETE` on a parent would now fail
loudly, which is the intended safety net.

### A8. Every FK points at `<table>(id)`

`304/304`. No composite FKs, no FK to a non-PK column.

## 3. Tier B — strong defaults (≥95%, with a coherent reason for each exception)

### B1. The five-column audit block

```sql
createdby  int4      DEFAULT 1     NOT NULL,
createdat  timestamp DEFAULT now() NOT NULL,
updatedby  int4      DEFAULT 1     NOT NULL,
updatedat  timestamp DEFAULT now() NOT NULL,
isdeleted  int2      DEFAULT 0     NOT NULL
```

**107/111 tables (96.4%) carry all five, verbatim.** Column order is stable: they sit as
a block near the end of the table, `isdeleted` last.

| Coverage | Count | Notes |
|---|---|---|
| `createdat` | 111/111 | |
| `createdby` | 110/111 | |
| `updatedby` | 107/111 | |
| `updatedat` | 107/111 | |
| `isdeleted` | 107/111 | |

**The four exceptions are all append-only log tables**, and the omission is principled —
a row that is never updated needs no `updatedby`/`updatedat`, and a row that is never
retracted needs no `isdeleted`:

| Table | Has | Missing |
|---|---|---|
| `partyledger` | `createdby`, `createdat` | update + delete block |
| `salesactivitylog` | `createdby`, `createdat` | update + delete block |
| `salespersonlocationlog` | `createdby`, `createdat` | update + delete block |
| `adminusercreationlog` | `createdat` only | everything else |

**Rule for a new table:** all five, always — *unless* the table is strictly append-only,
in which case `createdby` + `createdat` only, and say so in a comment.

`DEFAULT 1` on `createdby`/`updatedby` is a legacy convenience (user id 1) rather than a
statement of correctness; the models pass a real user id on every write. Keep the default
for consistency, don't rely on it.

Minor variance (4 tables): `partyledger.createdby` and `salesactivitylog.createdby` are
`int4 NULL` (system-written rows have no user); `superadminusermaster.createdby/updatedby`
are `int4 NULL`; `userotpmaster.createdby` is `int4 NOT NULL` with no default.

### B2. `organizationid` is the tenancy boundary

**67/111 tables** carry `organizationid int4 NOT NULL` (65) — the business tables. It is
always the **second column**, immediately after `id`.

The 44 tables without it fall into three clean groups:

1. **Platform-level / cross-tenant** — `usermaster`, `rolemaster`, `permissionmaster`,
   `modulemaster`, `planmaster`, `plandurationmaster`, `planlimitmaster`,
   `planlimittypemaster`, `planmodulemap`, `rolepermissionmap`, `apilimitmap`,
   `subscription*`, `superadminusermaster`, `organizationmaster` itself, `orginvitemaster`,
   `adminusercreationlog`, `usersessionmaster`, `userotpmaster`, `usersettings`.
2. **Line-item / child tables** — 14 of them (`invoicelineitem`, `grnlineitem`,
   `salesorderlineitem`, `purchaseorderlineitem`, `debitnotelineitem`,
   `salesreturnlineitem`, `vanreturnlineitem`, `bomlineitem`, `stocktransferlineitem`,
   `physicalcountlineitem`, `taxgrouplineitem`, `productionmaterialissue`,
   `paymentallocationdetail`, `purchaseorderattachment`, `customercontactmaster`,
   `suppliercontactmaster`, `salespersonrouteassignmap`). They inherit tenancy through
   their parent FK.
3. **A few contact/map children** as above.

> ⚠️ Group 2 is **not** universal — the two newest child tables, `grnlinebatch` and
> `invoicelinebatch`, *do* carry `organizationid`, while the older children
> (`invoicelineitem`, `grnlineitem`, `creditnoteitem`, `vanloadingmaster`, …) do not.
> The schema is genuinely split here. See D5.

Two tables have it **nullable on purpose**: `organizationsettings` (NULL row = platform
default, enforced by two complementary partial unique indexes) and `auditlogmaster`
(platform-level events).

`organizationid` almost always carries an FK to `organizationmaster(id)`; **5 tables have
the column without the FK**: `partyledger`, `salesactivitylog`, `creditnotemaster`,
`debitnotemaster`, `debitnotesourceinvoicemap` (*deviation, see D6*).

### B3. `isactive` is a separate, orthogonal flag

`40/111` tables, always `isactive int2 DEFAULT 1 NOT NULL`. **All 40 also have
`isdeleted`** — the two are never conflated.

- `isdeleted = 1` → the row is gone; it never appears in any list.
- `isactive = 0` → the row exists and is still referenced by history, but must not be
  offered for new use.

`isactive` belongs on **master/reference tables** (`productmaster`, `customermaster`,
`suppliermaster`, `warehousemaster`, `brandmaster`, `taxmaster`, `unitmaster`, …). It does
**not** belong on documents (`invoicemaster`, `grnmaster`, `salesordermaster`,
`paymentmaster` have none) — a document's lifecycle lives in its `status` column instead.

### B4. FK columns are `<referenced-entity>id`

`270/304` FK columns end in `id`; **223/304 (73%)** are literally
`<reftable minus the "master" suffix> + "id"` — `productid → productmaster`,
`customerid → customermaster`, `warehouseid → warehousemaster`.

The 34 that don't end in `id` are all **role-qualified pointers to `usermaster`**, and
that is itself a convention: `<verb>by`.

> `createdby`, `updatedby`, `invitedby`, `acceptedby`, `approvedby`, `rejectedby`,
> `cancelledby`, `postedby`, `paidby`, `voidedby`, `countedby`, `verifiedby`,
> `qualitycheckedby`, `collectedby`, `issuedby`, `deliveredby`, `refundedby`

When a table needs two FKs to the same target, it qualifies the prefix rather than
inventing a suffix: `baseunitid` / `salesunitid` / `purchaseunitid` → `unitmaster`;
`parentcategoryid` → `categorymaster`; `previousplanid` / `newplanid` → `planmaster`;
`billing*` / `shipping*` for the two address blocks.

11 FK columns use the `<fulltablename>_id` form instead — see D1.

### B5. Documents carry a `<doc>number varchar(50)`, unique **per organization**

24 document-number columns. The canonical shape is a per-org unique constraint or partial
unique index:

```sql
CONSTRAINT uq_invoice_number_per_org UNIQUE (organizationid, invoicenumber)
-- or, preferred for anything soft-deletable:
CREATE UNIQUE INDEX IF NOT EXISTS uq_<doc>_org_number
    ON <table> (organizationid, <doc>number) WHERE isdeleted = 0;
```

Already enforced this way: `productmaster.productcode`, `purchaseordermaster.ponumber`,
`grnmaster.grnnumber`, `salesordermaster.ordernumber`, `vansessionmaster.sessionnumber`,
`deliverymasterorder.deliverynumber`, `batchmaster` (org+product+batchno),
`creditnotemaster`, `debitnotemaster`, `supplierpaymentmaster`, `stocktransfermaster`,
`physicalcountmaster`, `productserial`, `vanmaster` (×2), `drivermaster`,
`stockadjustmentreason`, and every `*termmaster` / `*reasonmaster` code.

**Numbers are minted by `src/utils/docNumber.js`** using `pg_advisory_xact_lock` + `MAX()`
over a regex, *not* by a sequence and *not* by `COUNT(*)` (which the codebase explicitly
records as a fixed bug — see `scripts/doc_number_unique.sql`). Soft-deleted rows are
deliberately included in the `MAX`, so a number is never reissued.

### B6. Partial indexes filter on `isdeleted = 0`

**56 of 109 indexes** carry `WHERE (isdeleted = 0)`. Prefix convention:

- `idx_*` — 65 non-unique lookup indexes
- `uq_*` / `ux_*` — unique indexes and hand-named unique constraints
- `chk_*` — CHECK constraints (41 of 43; 2 are Postgres auto-names)
- `fk_*` — hand-named FKs (29 of 304; the other 272 use Postgres' `<t>_<col>_fkey`)
- `<table>_pkey` — every primary key

The most common shape is the tenant-scoped list index:

```sql
CREATE INDEX idx_<table>_org ON <table> (organizationid, isdeleted);
```

## 5. Table taxonomy — the five shapes

Table names are `<domain><role>`, all lowercase, singular, no separators.

| Suffix | Count | Meaning |
|---|---|---|
| `*master` | 66 | Any first-class entity — *including documents*. `invoicemaster`, `grnmaster` and `paymentmaster` are documents, not reference data; the suffix does **not** mean "lookup table" here. |
| `*lineitem` | 12 | Child rows of a document |
| `*map` | 8 | Junction / many-to-many |
| `*log` | 3 | Append-only |
| `*history` | 3 | Point-in-time snapshots |
| other | 19 | `partyledger`, `productserial`, `batchwarehousestock`, `paymentallocationdetail`, `supplierpaymentallocation`, `grnlinebatch`, `invoicelinebatch`, `usersettings`, `organizationsettings`, … |

Only 3 table names are plural (`usersettings`, `organizationsettings`,
`subscriptionpayments`) — all key-value or ledger-ish. Default to singular.

### 5.1 Master / reference table

```sql
CREATE TABLE IF NOT EXISTS public.<entity>master (
    id              serial       PRIMARY KEY,
    organizationid  integer      NOT NULL,
    <entity>code    varchar(20),
    <entity>name    varchar(150) NOT NULL,
    description     text,
    sortorder       int2         DEFAULT 0 NOT NULL,
    isactive        smallint     DEFAULT 1 NOT NULL,
    createdby       integer      DEFAULT 1 NOT NULL,
    createdat       timestamp    DEFAULT now() NOT NULL,
    updatedby       integer      DEFAULT 1 NOT NULL,
    updatedat       timestamp    DEFAULT now() NOT NULL,
    isdeleted       smallint     DEFAULT 0 NOT NULL,
    CONSTRAINT fk_<entity>_org FOREIGN KEY (organizationid)
        REFERENCES public.organizationmaster(id)
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_<entity>_org_code
    ON public.<entity>master (organizationid, <entity>code) WHERE isdeleted = 0;

CREATE INDEX IF NOT EXISTS idx_<entity>master_org
    ON public.<entity>master (organizationid, isdeleted);
```

### 5.4 Junction (`*map`)

```sql
CREATE TABLE IF NOT EXISTS public.<a><b>map (
    id        serial PRIMARY KEY,
    <a>id     integer NOT NULL,
    <b>id     integer NOT NULL,
    -- …audit block…
    CONSTRAINT <a><b>map_<a>id_<b>id_key UNIQUE (<a>id, <b>id)
);
```

9 columns is the typical width. When the pair can be re-created after a soft delete, use a
partial unique index instead of a constraint: `… WHERE isdeleted = 0`.

### 5.5 Append-only log

`id bigserial`, the payload columns, then **`createdby` + `createdat` only**. No
`updatedby`/`updatedat`/`isdeleted`. Say why in a header comment.

## 6. Constraint & index conventions

### CHECK constraints — 43 total

Two jobs, both worth copying:

**(a) Enum guards** (23) — always the `= ANY (ARRAY[...])` form:

```sql
CONSTRAINT chk_batch_status CHECK (((status)::text = ANY ((ARRAY[
    'active'::character varying, 'expired'::character varying,
    'quarantine'::character varying, 'consumed'::character varying,
    'returned'::character varying])::text[])))
```

**(b) Business invariants** (20) — non-negativity, date ordering, and mutual exclusion:

```sql
CONSTRAINT chk_delivery_dates      CHECK (deliverydate IS NULL OR deliverydate >= scheduleddate)
CONSTRAINT chk_spa_amount_positive CHECK (allocatedamount > 0::numeric)
CONSTRAINT chk_vanreturnli_damaged_qty CHECK (damagedquantity <= returnedquantity)
CONSTRAINT chk_paymentalloc_one_target CHECK (
    (invoiceid IS NOT NULL AND debitnoteid IS NULL) OR
    (invoiceid IS NULL AND debitnoteid IS NOT NULL))
```

Naming: `chk_<shortentity>_<subject>` — abbreviated, not the full table name
(`chk_inv_discounttype`, `chk_so_ordersource`, `chk_spa_amount_positive`).

### EXCLUDE constraints — 2

Used for temporal non-overlap, both gated on `isdeleted = 0`:

```sql
CONSTRAINT no_overlap_pricing EXCLUDE USING gist (
    productid WITH =, customercategoryid WITH =,
    daterange(effectivefrom, COALESCE(effectiveto, '9999-12-31'::date), '[)') WITH &&
) WHERE (isdeleted = 0)
```

Also on `salespersonrouteassignmap`. This is the house answer to "two dated assignments
must not overlap" — reach for it rather than an application check.

### Foreign keys

- 272 use Postgres' auto-name `<table>_<column>_fkey` (i.e. written as
  `REFERENCES` inline or as an unnamed constraint).
- 29 are hand-named `fk_<table>_<target>` — this is the style in newer hand-written
  migrations (`fk_grnlinebatch_org`, `fk_paymentmaster_depositaccount`).
- 3 legacy oddballs: `modulemaster_usermaster_fk`, `planmaster_usermaster_fk`,
  `updated_by_fk`.

**For new work: hand-name them `fk_<table>_<target>`.** It is what the last twelve months
of migrations do, and it makes `DROP CONSTRAINT` writable without a lookup.

## 7. How the tables are actually used (the other half of the contract)

Rules a DDL-only reader would miss. Measured across the 61 model files.

| Rule | Evidence |
|---|---|
| **Every `SELECT` filters `isdeleted = 0`** | 1 164 occurrences of `isdeleted = 0` / `isdeleted=0` |
| **Delete is `UPDATE … SET isdeleted = 1, updatedat = NOW(), updatedby = $n`** | 77 occurrences of `isdeleted = 1`, across 21 model files |
| **`updatedat` is set by hand on every UPDATE** | 312 occurrences of `updatedat = NOW()` / `= now()`. There is no trigger. Forgetting it is silent. |
| **Every business query is scoped by `organizationid`** | `WHERE organizationid = $1` / `= ANY($1::int[])` throughout; the org id comes from the `X-Org-Id` header via `resolveOrg` middleware |
| **Raw parameterized SQL only — no ORM** | `query(sql, params)` from `src/config/database.js`; only column/table *names* are ever interpolated |
| **Multi-statement writes use `withTransaction`** | posting/reversing documents, stock movement, allocations |
| **Concurrency on generated codes uses advisory locks** | `pg_advisory_xact_lock($classId, $orgId)` before `MAX()`-based numbering |
| **Column nullability is read from `information_schema`, not assumed** | `master.model.js` caches `columnMeta(table)` because sending `''` to a `NOT NULL` column produced 23502s |

`NOW()` is the uppercase spelling in application SQL (300 uses vs 12 lowercase `now()`);
`now()` is the lowercase spelling in DDL defaults. Both are the same function — match the
surrounding file.

## 8. Deviation register

Real inconsistencies, ordered by how much they'd cost to hit. Each is a decision a skill
should *not* propagate.

### D1 — `<table>_id` FK naming coexists with `<entity>id` · **25 columns, 2 pockets**

11 FK columns use `usermaster_id` / `subscriptionmaster_id` instead of the dominant
`userid`-style form: `userotpmaster`, `usersessionmaster`, `subscriptionmaster`,
`subscriptionpayments` (×2), `salespersonmaster`, `subscriptionhistory`,
`userorganizationmap`, `auditlogmaster`, `drivermaster`, `notificationmaster`.

A second pocket is the payment-gateway integration in `subscriptionpayments` /
`subscriptionpaymentmaster`: `provider_order_id`, `provider_payment_id`,
`provider_signature`, `gateway_response`, `payment_status`, `initiated_at`, `paid_at`.

Plus three strays: `suppliermaster.msme_registered`, `suppliermaster.msme_number`,
`productcosthistory.grn_referenceid`, `invoicemaster.pdf_generated_at`.

**Impact:** medium — auth and billing code reads `usermaster_id`, everything else reads
`<entity>id`. A generated query that guesses wrong 404s silently.
**Rule for new work:** `<entity>id`, no underscore. Don't "fix" the existing ones — they
are load-bearing in auth.

### D2 — Two PK strategies · **2 tables**

`creditnotemaster` and `creditnoteitem` use `int8 GENERATED BY DEFAULT AS IDENTITY`; the
other 109 use `serial4`/`bigserial`. Functionally equivalent, but `setval`-style repair
scripts and any tooling that reads `pg_get_serial_sequence` behave differently.
**Rule:** `bigserial`.

### D3 — One `timestamptz` · **1 column**

`salesordermaster.cancelledat timestamptz` against 276 `timestamp`. Mixing them in a
comparison silently applies the session `TimeZone`.
**Rule:** `timestamp` (no zone), matching everything else.

### D4 — One real `boolean` · **1 column**

`planmaster.isvisible bool DEFAULT true`. Every other flag in the schema is `int2` 0/1, so
frontend code that does `flag === 1` returns `false` for this column while every sibling
works.
**Rule:** `int2 DEFAULT 0|1 NOT NULL`.

### D5 — `organizationid` on child tables is inconsistent · **~16 tables**

Most `*lineitem` tables omit it and inherit tenancy from the parent; but the two newest
child tables, `grnlinebatch` and `invoicelinebatch`, carry it — while `invoicelineitem`,
`grnlineitem`, `creditnoteitem` and `vanloadingmaster` do not.
**Impact:** medium — a query written against one child cannot be templated onto another,
and a direct child-table scan without a parent join is untenanted.
**Rule for new work:** carry `organizationid` on children too (the newer tables do), and
index `(organizationid, isdeleted)`. It costs 4 bytes and removes a whole class of
tenancy bug.

### D6 — `organizationid` without an FK · **5 tables**

`partyledger`, `salesactivitylog`, `creditnotemaster`, `debitnotemaster`,
`debitnotesourceinvoicemap` carry the column but no `REFERENCES organizationmaster(id)`.
Nothing stops an orphan org id.
**Rule:** always add the FK.

### D7 — Unbounded `varchar` · **1 column**

`usermaster.fullname varchar NULL` — every other name column is bounded (150 or 200).
**Rule:** always give a length from the ladder in §4.

### D8 — `invoicemaster.invoicenumber` is globally unique, not per-org · **1 constraint**

```sql
CONSTRAINT invoicemaster_invoicenumber_key UNIQUE (invoicenumber)
```

Every other document number is `UNIQUE (organizationid, <number>)`. This one is a
**tenancy leak in reverse**: two organizations cannot both issue `INV-0001`, and the
failure surfaces as a confusing duplicate-key error in an unrelated tenant.
**Impact:** high — it will bite the first time two tenants use the same numbering scheme.
**Fix:** replace with `CREATE UNIQUE INDEX uq_invoice_org_number ON invoicemaster
(organizationid, invoicenumber) WHERE isdeleted = 0;`

### D9 — 22 `status` columns have no CHECK constraint

Only 23 of the ~92 enum-ish `varchar` columns are guarded. Unguarded `status` columns
include the busiest document tables in the system:

`invoicemaster.status`, `paymentmaster.status`, `salesordermaster.status`,
`purchaseordermaster.status`, `creditnotemaster.status`, `debitnotemaster.status`,
`salesreturnmaster.status`, `vansessionmaster.status`,
`vansessionmaster.reconciliationstatus`, `stocktransfermaster.status`,
`physicalcountmaster.status`, `productionordermaster.status`, `vanreturnmaster.status`,
`customervisitmaster.status`, `grnlineitem.qualitystatus`, `subscriptionmaster.status`,
`subscriptionpaymentmaster.status`, `subscriptionpayments.payment_status`,
`orginvitemaster.status`, `debitnotemaster.gstr1status`, `salesactivitylog.fromstatus`,
`salesactivitylog.tostatus`.

Meanwhile `grnmaster.status`, `batchmaster.status`, `productserial.status`,
`deliverymasterorder.status`, `supplierpaymentmaster.status`,
`purchaseorderlineitem.status` and `salespersondayschedule.status` *are* guarded.
**Impact:** medium — a typo'd status writes cleanly and then never matches a filter.
**Rule for new work:** always add `chk_<entity>_status`. The precedent for adding one to
an existing table is `scripts/grn_status_constraint.sql`.

### D10 — Schema snapshot is stale · **7 tables**

The DDL dump is 2026-08-06; `DB_SCHEMA.md` says 2026-08-07. Seven supplier-debit-note /
debit-note-payment tables and three `ALTER`-based hardening migrations post-date both.
**Fix:** re-dump and re-run `python3 scripts/gen_db_schema.py` after every applied
migration — the migrations themselves already say to.

## 9. Checklist for a new table

1. Name it `<domain><role>`, lowercase, singular, no underscores. Pick the suffix from §5.
2. `id` first — `serial4` for a master, `bigserial` for anything transactional.
3. `organizationid integer NOT NULL` second, with `fk_<table>_org` → `organizationmaster(id)`.
   Include it on children too (D5).
4. Business columns, using the type dictionary in §4. Bound every `varchar`.
5. Flags as `int2 DEFAULT 0|1 NOT NULL`, named `is*` / `can*` / `allow*`.
6. States as `varchar(20|30)` holding lowercase `snake_case`, **with** a
   `chk_<entity>_status` CHECK (D9).
7. `isactive int2 DEFAULT 1 NOT NULL` if it is reference data; omit if it is a document.
8. The five-column audit block, verbatim, at the end — or `createdby`+`createdat` only if
   append-only.
9. FKs hand-named `fk_<table>_<target>`, no `ON DELETE` clause.
10. `CREATE UNIQUE INDEX uq_<table>_org_<code> … WHERE isdeleted = 0` for any code or
    document number.
11. `CREATE INDEX idx_<table>_org ON <table> (organizationid, isdeleted)` plus a partial
    index for each hot filter.
12. In the model: filter `isdeleted = 0` and `organizationid` on every read; set
    `updatedat = NOW()` on every write; soft-delete only.

## 10. Migration file conventions

There is **no migration runner**. Files in `DMS-Backend/migrations/` are applied by hand
(DBeaver/psql), and the house style — visible in `20260813_session_hardening.sql`,
`20260807_supplier_debit_note.sql`, `scripts/grnlinebatch_multibatch.sql` — is:

- Filename `YYYYMMDD_<snake_case_topic>.sql` in `migrations/`; ad-hoc fix-ups go in
  `scripts/` with a plain descriptive name.
- A long `--` header block: **WHAT THIS IS**, why, the decisions locked and by whom, and
  an explicit statement of whether the migration is **behaviour-neutral on its own**.
- Numbered sections separated by `-- ═══…` rules.
- **Everything additive and idempotent**: `CREATE TABLE IF NOT EXISTS`,
  `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`. New columns are
  nullable-or-defaulted so the script can be applied ahead of the code.
- Long-form spellings in authored DDL (`integer`, `smallint`, `bigint`,
  `character varying(50)`, `timestamp without time zone`) with columns visually aligned —
  the short `int4`/`int2`/`varchar(50)` forms in §1–§6 are how `pg_dump` renders them back.
- Per-column `--` comments explaining anything non-obvious.
- A **Rollback** section at the end, commented out.
- Cutover steps that must run at deploy time (not at apply time) commented out and
  labelled as such.
- Closing note: *"Apply by hand (there is no migration runner), then re-run
  `scripts/gen_db_schema.py`."*
